# サイトの状態の確認（監視）

執行部ポータルの「サイトの状態」（/staff/status/）で、ホームページの自動更新がうまく動いているかを確認できます。
各項目は **正常／要確認／失敗** で表示され、失敗・要確認が上に並びます。

| 項目 | 内容 | 情報源 |
|---|---|---|
| 本番デプロイ状態 | mainの最新コミットが本番に反映されているか（30分を過ぎても反映されなければ失敗） | 定期チェック |
| 最終正常デプロイ | 公開中のビルドの日時とコミット | /build-version.json |
| 最新のお知らせ更新 | 執行部ポータルでの最終更新日時、記事ファイルの最新掲載日 | D1・記事一覧 |
| Facebookの最終取得成功 | 最後に投稿を取得できた日時 | SNS同期の記録（KV） |
| 最新のFacebook投稿 | 保存済みの投稿のうち最も新しい投稿の日時 | SNS同期の記録（KV） |
| SNS取得エラー | 失敗しているSNSと種類（例：「トークンの更新が必要」） | SNS同期の記録（KV） |
| 確認待ちのお知らせ | 新しいページの検知で自動作成された、未公開の下書きの件数 | D1 |
| サイト更新（自動処理） | GitHub Actions（新しいページの検知・SNS再ビルド）の最新の実行が失敗していないか | 定期チェック |
| RSS・お知らせ一覧の一致 | /rss.xml・/news/・トップページの内容と順番が一致しているか | 定期チェック |
| 定期チェック | 定期チェックが動いているか（3時間以上止まっていれば要確認） | 定期チェック |

## 定期チェック

- GitHub Actions「Site monitor」（`.github/workflows/site-monitor.yml`）が1時間ごとに `scripts/monitor/site-check.mjs` を実行します
- 本番サイトを読むだけで、サイトの内容・コード・設定は変更しません。GitHubの権限も読み取りだけです
- 結果は `/api/admin/site-health` に送られ、D1の `site_health_checks` に保存されます
  - 正常のまま変わらない項目は書き込みません
  - 正常から異常になったときだけ、`staff_audit_log` に `site.health` として記録します（毎回は記録しません）
- 秘密キーは新しいページの検知と同じ `NEWS_DETECT_SECRET` です。未設定の間は、結果をActionsのログに出すだけで送りません
- 手動で実行する場合：Actionsタブ → Site monitor → Run workflow

## 失敗・要確認のときの対応

- **SNS取得エラー「トークンの更新が必要」**：META_SOCIAL_SETUP.md の13章の手順で、管理者がアクセストークンを更新する
- **本番デプロイ状態が失敗**：Cloudflare Pages → nobeoka-ugokasu → デプロイ で、最新のビルドのログを確認する
- **サイト更新（自動処理）が失敗**：GitHubのActionsタブで、失敗したワークフローのログを確認する
- **RSS・お知らせ一覧が不一致**：数分後に解消しなければ、/rss.xml と /news/ を開いて比べる（D1の障害中は、RSSが記事ファイルだけになる）
- **確認待ちのお知らせ**：お知らせ管理（/staff/news/）で【確認待ち】の下書きを確認し、公開する

## テスト

- `npm run test:site-health`（D1はNodeのSQLiteで再現。Cloudflare・GitHubへはアクセスしない）
